# migrations

数据库迁移脚本已迁移到 **`internal/storage/sqlite/migrations/`**，并通过 Go 的 `embed`
嵌入程序，本目录不再保存 SQL 文件。

## 为什么移动

- 应用可以在任意工作目录下运行，迁移不再依赖外部 SQL 文件路径。
- 只维护一份迁移脚本，避免根目录与嵌入目录出现两份不一致的 schema。

## 约定

- 文件名以递增序号前缀开头，例如 `0002_add_retry_policy.sql`。
- 已发布的迁移不得修改，schema 变更只能追加更高版本的脚本。
- 每次 schema 变更必须同时提供迁移脚本，不允许只改代码。
- 迁移脚本只描述结构变更，不写入业务数据。
- 迁移由 `sqlite.Open` 在打开数据库时按版本顺序自动执行，已应用的版本记录在
  `schema_migrations` 表中，重复启动不会重复执行。
- 每个迁移在独立事务内执行，失败时整体回滚且不写入版本记录；并发打开同一数据库时
  只有持有写锁的一方执行迁移，其余进程检测到版本已存在后直接跳过。
- 表结构重建必须使用"建新表 → 复制数据 → 删除旧表 → 重命名 → 恢复索引与触发器"的
  受控流程，并在同一次迁移内完成。

## 数据库约束规范

`0009_relax_constraints.sql` 起，业务 Schema 遵守两条长期规则：

- **枚举字段不受数据库级封闭取值限制**：不使用 `CHECK (... IN (...))` 或等价形式限定
  状态、类型等枚举字段的取值集合，也不通过触发器重新实施白名单。未知取值必须能写入
  并原样读回，业务校验由 Go 层状态机承担。
- **禁止声明外键**：不使用列级 `REFERENCES`、表级 `FOREIGN KEY` 或任何 `ON DELETE` /
  `ON UPDATE` 级联行为，也不通过触发器模拟引用完整性。关联 ID 作为普通文本保存并保留
  索引，允许出现指向已不存在记录的孤立 ID。

主键、`NOT NULL`、有业务意义的 `UNIQUE`、非枚举性质的 `CHECK`（数值范围、长度、JSON
结构、跨字段组合一致性）与合理默认值继续保留。逻辑删除使用 `deleted_at` 标记，删除操作
不得级联删除历史记录。

`0009_relax_constraints.sql` 对全部业务表执行受控重建，并为 `roles` 与
`execution_hosts` 增加 `deleted_at`。`0001…0008` 保持原样，作为历史记录保留。

迁移状态与数据库文件位置见仓库根目录的 `README.md`。
