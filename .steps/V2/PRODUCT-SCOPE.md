# V2 产品范围

> 状态：V2 设计基线。上游依据：V1 最终状态见 [`../V1-final.md`](../V1-final.md)。

## 1. 产品目标

V2 不重写 V1 的执行流程，而是把发起工作的入口升级为**需求**：

```text
选择项目 → 对话提出需求 → AI 分析项目现状 → AI 生成实施方案并拆分为多个任务
→ 多轮对话调整 → 用户确认 → 原子创建 1 个正式 Requirement + N 个正式 Task
→ 用户手动启动 → 复用 V1 工作流执行 → 查看项目与需求进度
```

V2 的核心能力只有这五条：

1. 需求级规划对话（可多轮，同一会话内调整，不产生新需求）。
2. 基于真实项目代码的需求分析与方案生成（规划容器内只读代码）。
3. 结构化方案校验 + 原子生成 1 个 Requirement 与 N 个 Task（至少 1 个）。
4. 项目级调度：同一项目同时最多 1 个 Task，不同项目可并行，仍受全局并发上限约束。
5. 项目与需求视角的进度、任务与执行记录聚合查询。

## 2. 核心产品原则

- **Requirement 是用户希望实现的一项业务需求；Task 是实现它所需的一个独立执行单元。**
- 一个 Project 拥有多个 Requirement；一个 Requirement 生成 1..N 个 Task。
- Task 继续使用 V1 的 `Task → Step → Attempt → Session` 模型，不新增执行实体。
- **需求规划与任务执行是两个独立阶段**；生成 Task 不启动执行。
- 所有业务状态以数据库真实记录为准；模型不决定执行状态，不报告百分比。
- 规划阶段的一切产物都是**草案**，只有用户确认的那一版 Revision 才成为正式需求快照。

## 3. V2 非目标（硬性清单）

- 用户、用户组、角色权限管理与用户操作审计。
- 自定义 Agent 角色（角色固定四个，不可增删）。
- 已确认需求的修改、覆盖与重新规划。
- 自动删除并重建已执行任务。
- 自动回滚 Git 代码（Reset / Revert / 强制覆盖）。
- 任务之间自动合并分支、通用 Task DAG、任务自动串接。
- 第二套任务执行引擎或第二套验证判定规则。
- 通用插件化角色系统。
- 脱离真实使用数据的推测性性能优化。

任何请求若要求上述能力，先作为新阶段立项，不在 V2 内顺手实现。

## 4. 能力边界与已知限制

| 边界 | 说明 |
|---|---|
| 分支集成 | 项目内任务串行执行**不等于**解决分支集成；`merge_after_push` 仍默认关闭 |
| 任务拆分 | 规划必须避免把"强依赖前序未合并代码"的工作拆成多个独立 Task；不能安全独立验收的步骤合并为一个 Task |
| 需求变更 | 正式需求不可修改；纠正方式是停任务（显式停止并等待真实收敛）→ 删除需求（逻辑删除）→ 用户手动回滚 → 新建规划会话。DELETE 不隐式取消任务，未收敛时返回 409 |
| 代码回滚 | 删除需求只影响业务视图与调度，不代表 Git 仓库已恢复 |
| 权限 | V2 无认证与授权体系；服务仍只监听回环地址 |
| 私有仓库 | 认证由用户自定义执行镜像负责，不属于 AgentFlow 配置或产品能力 |

## 5. 进度语义

- 项目与需求进度只由正式 Task 的真实状态聚合，规则唯一实现在 `domain`（见
  [`WORKFLOW.md`](./WORKFLOW.md) §4）。
- 需求进度是**任务完成数量比**，不是"语义上的工作完成百分比"。
- 任一必要 Task 失败或 `recovery_required` 时，需求不得显示完成，必须显示阻塞/待恢复。
- 模型生成的总结不得覆盖真实执行状态。

## 6. 验收场景（M6 必须真实执行）

- **A 单需求多任务**：一个需求 → 多轮规划 → 确认 → 多个 Task 顺序执行 → 进度可见。
- **B 规划阶段只读**：文件工具与 Shell 两条路径的写入都被容器文件系统拒绝，且无提交记录。
- **C 不同项目并行**：两个项目同时执行，各自同项目串行，全局并发不超限。
- **D 同项目失败阻塞**：A1 失败/待恢复时 A2 不自动开始，B 项目不受影响。
- **E 需求删除**：运行中任务必须由用户显式停止并真实收敛，未收敛时 DELETE 返回 409（不隐式取消）；
  删除为需求与全部关联 Task 的原子逻辑删除，历史仍可查询，Git 不回滚、容器不被自动处置。
