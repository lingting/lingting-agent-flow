# V3 R3：并发调度与取消

**状态：** 待执行。
**上游文档：** [路线总规划](../ROADMAP.md)、[R2 资源管理器](../R2/README.md)。
**范围：** 让编排进程成为唯一并发决策者，并补齐取消、容量、互斥与迟到结果处理。不迁移既有用例
（R4.5 / R5）、不实现前端适配器（R6）、不改 `Makefile` / CI / `docs/`。

---

## 1. 目标

R1 是严格串行执行，`Case.Parallel` 只冻结了字段。本阶段交付：

1. 调度器：在同一个运行内决定并行度、排队顺序与资源互斥。
2. 容量：按资源类型限制同时在飞的用例数，超出即排队，不允许靠失败重试掩盖。
3. 取消：运行被中断时停止派发、终止在跑 worker 的进程树、回收资源、如实给出结论。
4. 迟到结果防护：已被判定终态的用例不接受后续结果文件覆盖。

R3 完成后，`t.Parallel()` 在新体系里没有任何作用，并发完全由调度器决定。

---

## 2. 输入（已冻结）

- 结论只有六种：passed / failed / skipped / panic / timeout / error（R1 §5、ROADMAP §1）。
- worker 是一次启动约 20ms 的子进程；单用例总开销约 30ms（R1 §8）。并发预算按此估算。
- 等待与终止：用例超时后先由 worker 的 deadline 接管，编排进程再用
  `taskkill /T /F /PID`（Windows）或 `kill(-pid, SIGKILL)`（非 Windows）兜底（R1 §7）。
- 资源分配只由编排进程完成；共享资源整次运行只分配一次（R1 + R2）。
- 现有并发基线是 `-p 8 -parallel 8`（`Makefile` 的 `PARALLEL ?= 8`）。
- `tests/integration/remote/workflow` 必须整包串行（R0 §6）；SQLite 迁移与连接在高并发下会超时
  （`Makefile` 的 `test-race` 注释记录了这一点）。

## 4. 实施步骤

### 4.1 调度输入模型
在 `Case` 或包级声明上补齐：`Parallel`（能否并行）、独占键列表、包级串行标记、资源类型容量。
输入只能来自用例声明与 R2 的冻结表，不允许调度器内置针对具体包的硬编码例外。

### 4.2 调度器
- 队列按确定性顺序（ID 升序）扫描，就绪即派发；同一批输入的结论顺序与串行执行一致。
- 满足以下全部条件才能同时运行：并行度未达上限、独占键不冲突、包级串行约束满足、所需资源容量可用。
- 共享资源获取必须串行化（同一声明只分配一次）；并发获取不得产生两份句柄。
- 不允许用「先启动再发现冲突再重试」的方式实现互斥。

### 4.3 容量与背压
- 每类资源声明容量；排队不改变结论，只增加等待时长，等待时长进入报告。
- 并发上限与资源容量取更严格的一方。
- 默认并行度与默认容量在阶段内定稿并写回本文，不允许隐式取 `runtime.NumCPU()`。

### 4.4 取消
- 第一次中断：停止派发新用例，向在跑 worker 发取消；等待宽限期。
- 宽限期后仍未退出：终止 worker 进程树，再回收资源。
- 取消不伪造结论：被中断的用例如实记录为 `error` 并注明「运行被取消」，运行级记录取消原因；
  不为取消新增第七种状态。
- 全局终检在取消后仍然执行；已分配的资源必须先释放再写报告。

### 4.5 迟到结果防护
worker 被终止后仍可能写出 `result.json`。编排进程只在用例结论未定型时接受结果文件；已判为
timeout / error 的用例不得被迟到结果改写（AGENTS 红线：迟到结果不得覆盖已确认终态）。

### 4.6 报告扩展
新增运行级并发观测：`parallel_limit`、`max_in_flight`、`queued_ms` 汇总、worker 启动次数。
用例级保留 R1 的 `timings`，并新增排队开始/结束时间，用于解释耗时差异。

### 4.7 9 个调度场景自检
`concurrencycheck` 组的 9 条用例必须覆盖下表，且不得用 `sleep` 猜时序，只能用显式信号、计数器或
阻塞点确认状态。

---

## 5. 9 个调度场景

| 编号 | 场景 | 判定 |
|---|---|---|
| 1 | 无资源用例并行 | 在飞数量达到上限，总耗时小于串行 |
| 2 | 同一独占键互斥 | 两条例程不重叠，报告显示等待 |
| 3 | 运行共享资源只分配一次 | 两条用例拿到同一句柄，分配计数为 1 |
| 4 | 包级串行 | 同组用例不重叠，跨组可并行 |
| 5 | 资源容量上限 | 超出容量的用例排队，不失败 |
| 6 | 用例超时 | 超时用例判 timeout，其余用例照常完成 |
| 7 | panic 隔离 | panic 只影响自身，运行继续并给出非零退出码 |
| 8 | 取消 | 不再派发、在跑被终止、进程树无残留、资源已释放 |
| 9 | 迟到结果 | 终止后写出的结果文件不得覆盖已判定的 timeout / error |

## 6. 阶段内需要冻结的决策

| 编号 | 决策 | 建议 |
|---|---|---|
| D1 | `--parallel` 语义 | 同时运行的 worker 上限，默认 8；资源容量可进一步压低 |
| D2 | 取消的结论表达 | 用例 `error` + message；运行级记录取消原因；不新增第七种状态 |
| D3 | 排队顺序 | ID 升序 + 就绪优先，保证同输入结论确定 |
| D4 | 共享资源并发获取 | 同一运行内串行化，不允许并发重复分配 |
| D5 | 默认资源容量 | 按 R2 声明；未声明容量的类型默认 1，必须显式放开 |

## 7. 运行授权申请

| 项 | 内容 |
|---|---|
| 允许执行的集合 | `selfcheck`、`selfcheck-fault`、`concurrencycheck`、`concurrencycheck-fault` |
| 允许的命令 | `./bin/agentflow-test --parallel <N> --artifact-dir .test-artifacts <集合>`；`tasklist` / `ps` 只读查看进程 |
| 明确不允许 | `tests/unit`、`tests/integration`、`tests/e2e` 的 `go test`；真实 Pi / SSH / 远程 Docker；前端命令 |
| 理由 | 调度语义可在自检组内完整覆盖；真实用例的并发正确性在 R4 / R4.5 验证 |

场景 8 需要核对进程残留，只允许只读列举进程，不允许用终止命令清理非本运行创建的进程。

## 8. 验收条件

1. 同一集合在串行与并行下的结论完全一致（通过/失败/跳过逐条对齐）。
2. §5 的 9 个场景全部通过，且不依赖固定等待时间。
3. 取消后：无遗留 worker、无遗留子进程、资源全部释放、终检执行、退出码非零。
4. 迟到结果无法覆盖已定型的 timeout / error 结论。
5. 报告包含并发上限、峰值在飞数、排队时长；同一输入两次运行的用例顺序一致。
6. 共享资源在并发下只分配一次；独占键冲突被调度器阻止而不是事后报错。
7. `go vet ./...` 与 `gofmt -l` 无新增问题（不运行测试）。

---

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| SQLite 与端口在高并发下超时 | 默认并行度 8；容量按资源类型收紧；不用重试掩盖阻塞 |
| Windows 进程树终止不可靠 | 回收失败判 `error`；不进「已杀」分支；场景 8 必须通过才进入 R4 |
| 场景自检本身易 flaky | 用信号与计数器代替 sleep；失败必须能稳定复现，不允许放宽断言 |
| 调度器内置包级例外 | 例外只能来自声明；`remote/workflow` 的串行声明由 R2 提供 |
| 取消路径上的资源泄漏 | 取消后仍执行终检；终检失败单独可见 |
