# 统一测试执行器路线图审阅

**审阅对象：** AgentFlow 统一测试执行器重构路线图 R0.1
**审阅基线：** `master` / `e98a8a123b92f7bf6edfad803dc66765b3b0b1c5`（工作区干净）
**审阅日期：** 2026-11-10
**审阅范围：** 仅评估路线图的可行性、风险与需要修订的条目；不产出 R0 资产清单，不修改代码。

---

## 一、总体结论

方向成立：把测试的并发决策权、资源生命周期和报告收口到一个 Runner，符合当前仓库的实际痛点——
`Makefile` 已经把并发度压成 `-p $(PARALLEL) -parallel $(PARALLEL)` 一个全局旋钮，
`go-test-groups.sh`（13.9K）的存在本身就是"按包分组以规避资源竞争"的补丁，
前端另有一套 `test-resource-policy.ts`。三套调度并存，确实是需要收口的。

但路线图当前版本**不能直接进入 R0**，原因有三类：

1. **一个目标与 Go 语言事实冲突的量级被低估了一个数量级**：R5 不是"迁移 `testing.T` 依赖"，
   而是重写 1705 个测试函数、约 9800 处断言调用点（详见 P0-1）。这是全流程唯一的主要成本项，
   路线图只用一条 bullet 描述。
2. **执行模型缺少一个关键决策：Case 是否在 Runner 进程内执行**。单进程模型会同时破坏
   包级隔离、panic 隔离、进程级日志捕获和 race 检测（详见 P0-2）。
3. **两项现有能力在新体系中无处安放**：`go test -race` 与 `-cover`（详见 P0-3）。

以及一处**流程自相矛盾**：R1 起的每个阶段都要靠"运行测试"来验收，而路线图第八章第 7 条又规定
未经授权不得运行测试。若不在每阶段显式授权，R1–R9 的退出条件全部无法判定（详见 P0-5）。

以下按阻塞项（P0）、高风险项（P1）、修订建议（P2）分级，最后给出需要决策的四个问题。

## 三、阻塞项（P0）

### P0-1 `testing.T` 无法由 Runner 实现，R5 的量级被低估

Go 的事实约束：

- `testing.TB` 接口含未导出方法 `private()`，因此只有 `*testing.T` / `*testing.B` / `*testing.F`
  能满足它；外部包**无法实现** `testing.TB`。
- `*testing.T` 的值只能由测试框架内部构造，外部无法创建有意义的实例。
- `testing.M` 同理：`testing.MainStart` 的参数类型 `testDeps` 是未导出接口，外部无法传入。

推论：**只要测试代码仍写在 `_test.go` 里、仍依赖 `testing`，就只能由 `go test` 驱动。**
不存在"自己写 Runner 把 `testing.T` 塞进去"的桥接方案。路线图 R5 的"迁移"实际含义是：
把 1705 个测试函数改写成接受自定义上下文（例如 `*testkit.C`）的普通 Go 函数，
并替换约 9800 处 `t.Fatal*` / `t.Error*`。

这不是不可行，而是**它是整个重构 80% 以上的工作量**，且是纯机械劳动，几乎不产生产品收益。
路线图把它和"统一报告"这类小项并列为 R5，会让排期和验收都失真。

可选路径，建议在 R0 冻结接口前明确选定一条：

| 路径 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A. 全量重写 | 见上述 | 1705 个函数 + 9800 处调用点 | 改写期回归判定依赖人工；`t.Helper`/`t.Run` 语义需自行重建 |
| B. Runner 内部调用 `go test` | Runner 负责资源、调度、报告，Go 用例以"包 + `-run` 正则"为单位执行 | 无改写成本 | 与完成标准 9（不得用 `go test`）冲突；并发粒度只能到包级 |
| C. 分层：`_test.go` 保留纯函数级单测，集成/E2E 迁移 | 只迁移 82+7 个集成/E2E 文件 | 中等 | 完成标准 9 需要改写为"不再用 `go test` 作为**集成测试**执行器" |

**建议选 C**：`tests/integration/` 与 `tests/e2e/` 本来就是子进程/真实资源驱动，迁移到 Case 模型
收益最高（资源声明、互斥、清理核验都在这一层），而 `tests/unit/` 的 157 个文件是纯函数测试，
改成自研上下文后并发与资源收益接近零，却要付出约八成的迁移成本。
若产品上必须满足完成标准 9，则应把它从"目标"降级为"可选择执行的 R10"，不要压进主线。

### P0-2 执行模型缺少"进程内还是子进程"这个决策

路线图 3.6/3.7 只规定了"调度器唯一决策"，没有规定 Case 在哪个进程里执行。这决定了其余所有设计：

现状事实（证据）：

- `tests/internal/testkit/main.go` 的实现方式是**进程级 fd 重定向**：先保存真实
  `os.Stdout`/`os.Stderr`，再把当前进程的 fd 换成管道，写入 `<run>/test.log`。
  这依赖"一个测试包 = 一个进程"这一前提。
- 现在 35 个测试包 → 最多 35 个独立进程，包级全局状态（`sync.Once`、包变量、slog 默认 handler）
  天然隔离。
- 单个测试文件最大规模：`tests/unit/app` 41 个、`tests/integration/local/workflow` 19 个、
  `tests/integration/remote/planning` 13 个。

若 Case 在 Runner 进程内执行，会同时出现四个问题：

1. **包级隔离消失**：246 个文件的包级状态、`init()` 顺序、`sync.Once` 全部在同一个进程里，
   原本靠"不同测试二进制"隐式隔离的东西会开始互相影响。
2. **panic 与 `os.Exit` 会杀死整个 Runner**，之后既没有报告也没有资源回收——
   这与 R9 要求的"进程异常退出后的资源清理核验"直接冲突。
3. **per-case 日志无法用 fd 重定向实现**：并发写入同一个 fd 无法按用例分流；
   改用带前缀的并发 writer 后，`t.Helper` 之外的输出（slog、exec 子进程、Docker CLI）
   不具备前缀归属信息。
4. **race 检测按进程编译期开启**（见 P0-3），无法按 Case 开关。

**建议明确采用两段式模型**：

```text
agentflow-test（编排进程）
├── 资源管理器（本进程）：容器、SQLite、服务进程、镜像、SSH
├── 调度器（本进程）
└── worker（子进程，每 Case 或每批次一个）: agentflow-test --exec-case <id>
    ├── 独占 stdout/stderr → cases/<case-id>/{stdout,stderr}.log
    ├── 包级全局状态隔离
    ├── panic / os.Exit 只影响该 Case，编排进程照常回收资源
    └── 可按需以 -race 构建/运行
```

这个模型还顺带解决：R2 的"资源最终状态无法确认时必须报失败"（子进程退出码 + 资源快照比对）、
R3 的"Runner 取消后不留子进程"（终止 worker 进程树）、R9 的"异常退出后清理"。

代价：跨进程传递资源句柄（容器 ID、端口、DB 路径）需要序列化。这一条应写进 R1 的接口设计，
不要等到 R3 才发现。

### P0-3 `-race` 与覆盖率在新体系中没有归属

路线图 R8 要求删除 `Makefile` 的 `test-race`，但新体系中没有任何等价能力，而现有
`test-race` 目标确实在跑两个真实范围：

```make
test-race:
	go test -race -count=1 -p $(PARALLEL) -parallel $(PARALLEL) ./tests/unit/...
	go test -race -count=1 -p $(PARALLEL) -parallel $(PARALLEL) ./tests/integration/local/ssh/...
```

race 检测是编译期特性，Runner 运行时无法打开。必须在设计上给出方案，否则这是能力回退：

- 方案一（与 P0-2 一致）：worker 二进制提供 `-race` 构建变体（`go build -race`），
  Runner 参数 `--race` 决定 worker 使用哪个变体；同一批 Case 的 race 报告作为产物收集。
- 方案二：明确写"删除 race 门禁"为**已接受的能力回退**，并在 `docs/testing.md` 与 CI 中同步移除。

覆盖率同理：现在没有 `-cover` 目标，若后续想加，方案一的 worker 模型同样适用；
若不加，也应在路线图中显式声明"本次重构不保留覆盖率能力"，避免 R9 才发现。

### P0-4 旧 `TestMain` 承担的收尾核验在新模型中归属不清

35 个 `TestMain` 不只是"初始化"，其中包含 `testkit/finalize.go` 的**零残留核验**：
真实测试结束后检查容器、远程目录、工作空间、SSH 连接是否全部清理干净，未清理则失败。

路线图 R7 把"清理登记、所有权核验、零残留检查迁移为资源生命周期的一部分"写成一条 bullet，
但零残留核验的对象是**整个运行**（跨 Case、跨资源），不是单个资源。它需要一个明确的落点：

- 是资源管理器退出时的全局终检？
- 还是每个 Shared 资源清理后的逐项核验 + 汇总？
- 核验失败时报告到哪个层级（资源结果、运行结果、还是两者）？

这一条必须在 R2 接口冻结前定义，否则 R7 会在迁移中途返工。建议：
**资源级核验（每个资源停止后自证消失）+ 运行级终检（编排进程退出前做一次全量快照比对）**，
后者失败时整体退出码非零，并保留此前所有产物。

### P0-5 路线图与"未经授权不得运行测试"的约束自相矛盾

第八章第 7 条：未经用户明确授权，不运行测试。而：

- R1 退出条件要求"可以执行多个简单 Case"、"能生成统一报告"；
- R3 退出条件要求验证 9 个并发调度场景；
- R4 要求试点跑通 `server.shutdown`；
- R9 要求全量验收。

这些全部是"必须运行测试才能判定"的条件。若继续按"不授权就不跑"执行，则每个阶段的退出条件
都只能靠代码阅读宣称达成——这正好违反了第八章第 10 条（不得将未执行、跳过或失败的测试报告为通过）。

**建议修订**：把"每阶段验收需要运行哪些 Case"作为该阶段的**授权请求**写入阶段说明，
由你在阶段开始时一次性授权（授权范围 = 该阶段的验收用例集合），而不是笼统的"不得运行测试"。
否则路线图在流程上无法自洽。

## 四、高风险项（P1）

### P1-1 Windows 进程树终止

目标环境是 Windows 11 + Git Bash。R3 要求"Runner 被取消时，不留下仍运行的子进程"，
在 Windows 上必须显式处理进程树：`exec.Cmd` 的 `Kill()` 只杀直接子进程，
配合 `Taskkill /T /F` 或 Job Object（`windows.CreateJobObject`）才能覆盖
`go test → 测试进程 → Pi CLI → Docker CLI` 这条链。routes 里已有的
`testkit/remotecontainer.go` 说明远程链路本来就有多层子进程。这一条应写入 R2/R3 的实现约束，
而不是留给 R9 验收才发现。

### P1-2 前端适配器的实际形态

`playwright.config.ts` 与 `vite.config.ts` 的现状决定了适配器不能只写"workers=1"：

- Playwright 侧：`webServer` 自动拉起 `vp dev`，`workers` 由 `test-resource-policy.ts` 决定，
  `fullyParallel: false`，产物写入随机 `TEST_ARTIFACT_DIR`。迁到 Runner 后要移除 `webServer`
  （前端服务变成 Shared 资源），并把 24 个 spec 的并发决策交给调度器。
- Vitest 侧：`maxWorkers` 同样来自 `test-resource-policy.ts`，`include: ["tests/**/*.test.ts"]`。
- 进程开销：若"一个 Case = 一个 spec"，24 次 Playwright 启动 + 13 次 Vitest 启动，
  每次都有 Node + 浏览器冷启动。**建议明确"一个 Case = 一个 spec 文件"**，
  文件内串行、文件间由调度器并行，并在 R6 前先测一次冷启动开销，避免改成比现在慢一倍的体系。
- 程序化调用方式也要定：Vitest 有 `startVitest` Node API；Playwright 的 `@playwright/test`
  程序化入口有限，更现实的是 `playwright test --workers=1 --grep` 子进程调用。
  这两条路径的产物收集方式不同，应在 R6 前确认，别在实现中临时切换。

### P1-3 "覆盖没有静默丢失"缺少可检查手段

完成标准 14 要求"原有测试场景和断言没有因迁移而静默丢失"。当前只有人工清单，
无法判定。建议在 R0 就把对账物做成**可执行**的：

1. R0 用 AST 解析 `git ls-files '*_test.go'` 下全部 `func Test*` 与 `t.Run` 字面量，
   生成冻结清单 `legacy-cases.manifest`（含包路径、函数名、子测试名）；
2. R5/R7 的退出条件改为"新注册表覆盖 manifest 全集"，由 `agentflow-test --audit-coverage`
   （或一个 `go vet` 之外的一次性核对命令）逐项比对；
3. 允许 manifest 条目显式标记为 `dropped: <理由>`，但不允许"消失"。

没有这份 manifest，"没有静默丢失"只是声明。

### P1-4 `t.Parallel()` 语义必然降级，需要显式接受

1744 处 `t.Parallel()` 在新模型里无法等价：Go 的 `t.Parallel()` 有父子同步语义
（父测试挂起直到并行子测试结束，且与同包并行测试共享进程）。改成"由调度器决定"后：

- 好处：符合路线图 3.6 的唯一决策者原则；
- 代价：若某些测试**依赖** `t.Parallel()` 造成的时序（例如依赖前一个测试留下的共享状态），
  语义变化可能让它们从"偶尔失败"变成"稳定失败"，或反之掩盖竞争问题。

建议在 R5 记录一次迁移判定：`t.Parallel()` 一律映射为 Case 的可并行属性，
并在 R0 盘点时标记"疑似依赖并行时序"的文件（可用 `sync.Once` / 包级变量 / 固定端口 /
固定路径四类特征粗筛，现有 `sync.Once` 8 处、固定端口见于 Playwright `26390`）。

### P1-5 资源共享与前端的可写状态冲突

路线图允许 `Shared + NamespacedWrite`。前端 Vite dev server 是典型例子：
24 个 spec 共享一个 dev server 时，任何写操作（上传、状态残留、localStorage）都会跨用例污染，
而 Playwright 的页面上下文隔离只覆盖浏览器侧，不覆盖服务端侧。
建议 R6 明确：E2E 用例对共享后端的写操作一律需要 `NamespacedWrite` 且命名空间可验证，
不可验证的用例改为独享后端——这会提高资源成本，反过来影响 R4 的试点结论。

### P1-6 镜像"共享"与"构建即写入"的冲突

3.4 已经指出镜像要按内容指纹缓存、不能等同于运行期 Shared，但没解决一个具体冲突：
**构建镜像本身是对 Docker daemon 的写入**，属于 `Destructive` 语义边缘。
若同时遵循"禁止 `Destructive + Shared`"和"多用例共享镜像"，则镜像构建必须走单独的
"缓存产物"通道（构建一次 → 打标签 → 用例只拉取只读标签），并明确"谁负责删除过期标签、
是否允许 `docker rmi`"。当前路线图把 Docker 镜像列为 Shared 资源，与 3.3 的组合禁令存在张力，
建议在 R2 里把"构建产物缓存"与"共享资源"两个概念分节写清楚。

### P1-7 选择语义与既有命令行的映射缺失

现有开发者习惯会失效，需要逐项给替代：

| 现有用法 | 新体系需要 |
|---|---|
| `go test -run 'TestFoo' ./tests/unit/store/...` | `agentflow-test store/TestFoo` 或 `--tag store` |
| `go test -count=1` | Case 默认不复用结果，是否保留 `--count` 需明确 |
| `go test -short` | 目前 0 处 `testing.Short()`，可直接声明不支持 |
| `go test -timeout 10m` | R1 已声明"用例超时"，需给出默认值与覆盖方式 |
| `-race` | 见 P0-3 |
| `-p / -parallel` | R3 的全局并发参数，需说明二者是否合并为一个 |

## 五、修订建议（P2）

1. **阶段顺序**：把 R5 从主线移出，或在 R4 之后插入一个"R4.5 Go 集成测试试点"
    （只迁 `tests/integration/local/` 的 51 个文件中的一个子目录，例如 `local/scheduler` 8 个），
   用真实场景验证 Case API 后再决定 `tests/unit/` 是否改写。R5 的"全量迁移"作为最后一个阶段，
   且必须在 P0-1 的路径决策之后。
2. **R0 交付物可执行化**：除人工清单外，产出 `legacy-cases.manifest` 与
   `case-resource-matrix.json`，后者供调度器（R3）直接读取，避免两次人工整理。
3. **R1 增加"进程模型"决策记录**：明确编排进程 vs worker 子进程边界、句柄序列化格式、
