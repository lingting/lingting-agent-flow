# V3 R4.5：Go 集成测试单子目录试点

**状态：** 待执行。
**上游文档：** [路线总规划](../ROADMAP.md)、[R4 真实服务进程试点](../R4/README.md)。
**范围：** 只迁移 `tests/integration/local/scheduler`（8 个文件，其中 6 个含用例，共 41 个用例）。
不迁移其他包（R5）、不实现前端（R6）、不改 `Makefile` / CI / `docs/`。

---

## 1. 目标

R4 只证明机制可用。本阶段用**既有集成用例**验证四件事，并据此决定 R5 是否进入批量迁移：

1. Case API 是否够用：迁移 41 个用例会暴露缺什么（清理栈、子测试、辅助函数签名）。
2. 迁移成本是否可接受：人工改写的工作量、语义风险与返工比例。
3. 结果是否等价：新执行器与 `go test` 在同一范围内的通过/跳过逐条对齐。
4. 资源声明是否准确：R2 判定 `local/scheduler` 为共享、只需 `sqlite-db`，试点是第一次校验。

试点结论不通过时停止，向用户反馈成本与阻塞项，不擅自扩大或缩小迁移面。

---

## 2. 输入与事实

- 目标包：`tests/integration/local/scheduler`，8 个文件（`main_test.go`、`helpers_test.go` 与 6 个用例文件），
  41 个 `func Test*`，资源只有 SQLite，无真实依赖（R0 §4.1）。
- R0 冻结清单中该包有 41 条用例，是本次试点覆盖对账的分母。
- 该包初判可共享；R0 标记 `concurrency_acceptance_test.go` 含 `sync.Once`，迁移后需人工判定是否依赖时序。
- 现有测试辅助全部以 `*testing.T` 为参数：`testkit.Dir`、`testkit.ConfigPath`、`testkit.Load*Config`、
  `testkit.OpenSQLite` 等，且 `testkit.Main` 承担日志与工作空间初始化。
- R1 的 `Context` 目前没有 `Cleanup`、没有子测试、没有 `Helper`；这三个缺口会在本阶段暴露。
- `t.Parallel()` 在新体系中只映射为调度属性，不再产生父子同步语义。

## 4. 实施步骤

### 4.1 先补齐 Context 缺口
- `Cleanup(func())`：Case 结束按后进先出执行；清理失败记为用例失败；panic 与超时也必须执行已注册清理。
- 子测试：保留块内顺序执行语义并记录名称，用于与 manifest 的子测试条目对账；不拆成独立 worker。
- 辅助定位：`Helper()` 语义用于失败定位，至少保证 `c.Fatalf` 的调用点可读。

### 4.2 冻结辅助函数的复用策略
现状是 `testkit` 全部接收 `*testing.T`，直接迁移会让 41 个用例连带改写大量辅助调用。三条路径：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A 全量改写 | 每个 helper 调用改成新签名 | 41 个用例 + 全部 helper | 改写面最大，容易引入行为差异 |
| B 最小接口适配 | `testkit` 改收 `Tester` 接口；`*testing.T` 天然满足，`Context` 补实现 | 改动集中在 helper 签名 | 接口覆盖须完整 |
| C 复制 helper | 新写一套 `casekit` | 复制 20K 辅助逻辑 | 两套实现长期并存，违反单一职责 |

建议选 B：`*testing.T` 与 `Context` 都能满足同一接口，unit 侧零改动，集成侧调用点几乎不变。
本阶段必须验证接口方案在 41 个用例上真的成立，否则退回 A 并在本文记录原因。

### 4.3 迁移顺序
1. `main_test.go`：拆解 `TestMain` 的职责（运行根目录、日志、最终核验），把仍需要的部分转为
   Case 初始化或资源声明。
2. `helpers_test.go`：确认辅助函数在接口方案下可直接复用。
3. 6 个用例文件：按「一个既有 `func Test*` = 一条 Case」逐条迁移；表驱动子测试保留为 Case 内顺序块。

### 4.4 资源声明
每个 Case 声明一条 `sqlite-db`（`case-exclusive`），数据库文件落在 `c.TempDir()` 下。
不得复用同一个数据库文件；不得依赖 `testkit` 的运行根目录全局状态。

### 4.5 对照运行
在同一范围内跑一次 `go test ./tests/integration/local/scheduler/... -count=1` 作为对照基线，
逐条比较：结论、跳过原因、失败位置。差异必须逐项解释；不得用「大概一致」收尾。

### 4.6 记录成本与阻塞项
记录人工迁移耗时、遇到的语义问题类型、补 API 的次数，用于 R5 排期判断；不以行数作为成果证据。
若单条用例平均成本明显超出预期，停止并向用户报告，不擅自改变迁移范围。

## 7. 验收条件

1. 41 条用例全部注册，与 R0 清单逐条对齐；不存在无主条目。
2. 新执行器与 `go test` 对照结果一致；差异全部有解释与处置。
3. 同一集合连续三次运行结论一致，无偶发失败。
4. `Context.Cleanup`、子测试记录、失败定位在试点中验证通过；辅助函数复用方案成立。
5. 资源声明准确：无额外共享、无跨用例数据库复用；终检 `passed`。
6. 试点结论文档化：迁移写法、成本、阻塞项、对 R5 的批次建议。
7. `go vet ./...` 与 `gofmt -l` 无新增问题（除 §6 授权的对照运行外不运行测试）。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| `sync.Once` 与包级状态在单进程内失效 | 迁移时把这些状态降级为 Case 内局部状态；逐文件确认 |
| 子测试语义变化导致结论漂移 | 保留 Case 内顺序执行；子测试名与清单对账 |
| 辅助函数接口方案不成立 | 试点内验证，失败即回退方案 A 并记录 |
| 试点成本被低估 | 先迁 5 条用例做样本，再决定是否继续；超出预期即停 |
| 试点通过被误读为「R5 一定可行」 | 结论只覆盖 1 个包 41 条用例；R5 按批次继续验证 |
